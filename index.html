why the next command takes a minute

one file writes the shopping list. one command does the shopping.

package.json → node_modules

no real project writes all its own code. ours borrows things other people already built, and it keeps a written list of exactly which ones in a file called package.json. that list is the next slide, and you can read it.

npm install reads that list, downloads every item on it, and drops them all into a folder called node_modules. that folder is 364 megabytes and nobody ever opens it, edits it, or uploads it, because it can always be rebuilt from the list.

the file is the shopping list, the folder is the shopping. the reason this matters to a PO: "it works on my machine but not on the server" is very often somebody's shopping list being out of date. don't pre-empt the next slide, which shows the actual file.

a word you've definitely heard in standups · and it's simpler than it sounds

every computer on a network has a number. names are just easier to remember.

localhost = 127.0.0.1

when you type google.com, your browser does not know what that means. it looks the name up and gets back a number, an address, and talks to that. the name is a convenience for humans. the number is the real thing.

localhost is the same trick, pointed at yourself. it is a nickname for 127.0.0.1, which every computer reserves to mean "this machine, right here". so localhost:3000 is: this very laptop, at door number 3000. type 127.0.0.1:3000 instead and you get the identical page.

have them actually type 127.0.0.1:3000 once the site is up, it takes five seconds and the penny drops audibly. the domain-name comparison is the part that makes it click, because they already trust that google.com is not literally a place. and this is the slide that explains "works on my machine": the site is real, it just lives at an address only they can reach.

the two most confused words in software

git is on your laptop. github is a website. they are not the same thing.

git · github

git is a program on your machine that remembers every version of every file. github is a website where those histories get uploaded, shared and combined. you can use git with no internet at all. github is where the team meets.

this confusion causes more PO/dev miscommunication than anything else on the list. useful line: git is the camera, github is the shared photo album. if you only teach one distinction today, teach this one.

plain english first · the names they use come second

what you look at, what fetches it, and where it's kept

the screenthe part you can see and click. the page sitting on your localhost right now. devs call it the ui, the front end, or the client.

a word you'll hear in a panicked voice one day · and why it did not happen to you

when two people edit the same line, git refuses to guess

IF WE ALL SHARED ONE FILE{ name: "sara", emoji: "🌙" },
TWO PEOPLE, SAME LINE{ name: "omar", emoji: "⚡" },
CONFLICT (content): Merge conflict in src/data/team.ts git is not broken and neither is anybody else. it's asking a question: which of these two lines should survive?

every one of you just merged into main without seeing that. not luck: this project gives each person their own file, so no two branches ever touched the same line. somebody chose that on purpose. a real one takes a dev about a minute to resolve, and it happens most weeks on most teams.

explain this one on the projector, do not stage it. we're deliberately not creating real conflicts today, there isn't time to walk fifteen people back out of one. what matters is that they stop hearing "merge conflict" as a disaster: it's git asking a question, and the answer is a human choosing. if someone wants to see one resolved, that's a five-minute follow-up over their shoulder another day.
the last two words of the day

merge makes it real. deploy makes it visible.

merge → deploy

merging folds your branch back into main. that alone doesn't put it in front of anyone. deploying is the separate step that copies it onto the servers users actually reach, and on this project it happens automatically, about forty seconds after the merge.

merge and deploy being two different things is the distinction POs most often collapse. "it's merged" and "it's live" are different sentences, and the gap between them is where a lot of PO/dev confusion lives.
